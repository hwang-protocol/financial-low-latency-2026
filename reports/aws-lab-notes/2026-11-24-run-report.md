| L2 | 2 MB（每核） |
| L3 | 105 MB（共享） |

**缺页实验：** 用 `mmap` 申请 128 页匿名内存，逐页写 1 个字节，次缺页计数正好增加 **128**。说明 `mmap` 只是“领了地址”，每页**第一次写**时内核才真正分配物理内存。这就是交易程序启动时要**预先把内存全部碰一遍**（预热）的原因。

**vCPU 拓扑（第 04 章要用）：** CPU 0 和 2 在同一个物理核上，1 和 3 在另一个物理核上。

## 第 04 章：C++ 线程交接（队列、忙轮询、CPU 绑定）

数据：[20261124T1013Z-04-software/](../aws-runs/20261124T1013Z-04-software/)

### 怎么做的

- 用课程的测量程序 `software_measurement.py`，**参数和课程完全一样**：每组 8 轮，每轮预热 40 笔、正式 400 笔，间隔 20 ms；AUTO 交易员同时下对照单，用来监测环境
- 只改了 3 处（见 `aws-patch.diff`）：
  1. 课程用 `ssh root@10.1.1.2` 去绑核，AWS 上测量程序就跑在 `.2` 本机，直接执行
  2. 行情模式从“只发 A 路组播”改成 UNICAST
  3. IP 换成 AWS 内网地址
- CPU 安排和课程一样：MANUAL 下单线程在 CPU 2，AUTO 在 CPU 3，其他线程在 CPU 0–1。测量程序自己固定在 CPU 1

### 结果（交接段 p99，也就是最慢 1% 的耗时）

| 运行 | 对比 | 交接 p99 | 差异 95% 置信区间 | 方向一致 | 课程判定 |
|---|---|---|---|---|---|
| ① | deque + 锁 + 条件变量 | **47.1 µs**（8 轮从 29.2 到 239.6 µs） | — | — | ❌ 轮间相差 8.2 倍（门限 1.5） |
| ② | deque **vs** 固定格子（都用锁 + 条件变量） | 62.2 vs 72.6 µs | −42.3 ~ +36.8 µs，**分不出快慢** | 不适用 | ❌ 16 轮中 6 轮环境漂移 |
| ③ | 固定格子 + 条件变量 **vs** 无锁 SPSC + 忙轮询 | **114.1 vs 2.4 µs** | +72.3 ~ +146.2 µs，忙轮询更快 | **8/8** | ❌ 16 轮中 3 轮环境漂移 |
| ④ | 忙轮询：独占 CPU 2 **vs** 挤在 CPU 0 | **2.3 vs 42.9 µs** | 独占快 35.6 ~ 44.9 µs | **8/8** | ❌ 16 轮中 1 轮环境漂移 |

另有一次**没给测量程序绑核**的运行 ①（在 `unpinned-attempt/` 里）：交接 p99 是 **255.4 µs**。测量程序占满 100% CPU、到处乱跑，干扰了交易线程。

### 和课程物理实验台对比

| | 课程（物理机） | AWS（c7i.xlarge） |
|---|---|---|
| 锁 + 条件变量 | 约 17 µs | 47–114 µs |
| 无锁 + 忙轮询（独占核） | 约 6.8 µs | **2.4 µs** |
| 忙轮询挤在共享核 | 约 57–65 µs | 42.9 µs |
| 忙轮询快多少倍 | 约 2.5 倍 | **约 47 倍** |

### 学到的

1. **“睡着等叫醒”在虚拟机里特别贵。** 线程睡着后，它的 vCPU 也跟着进入空闲，要叫醒就得经过虚拟机管理程序（hypervisor），一来一回几十到上百微秒。忙轮询的线程一直醒着，不受影响。所以在云上，忙轮询的优势比物理机还大
2. **忙轮询本身在新 CPU 上很快：** 2.4 µs 比课程的 6.8 µs 还低，因为 c7i 的 CPU（Sapphire Rapids）更新
3. **忙轮询必须独占一个核。** 挤到共享核上，要和别的线程轮流用 CPU，p99 一下涨了 18 倍
4. **只换队列的存储方式（deque 换成固定格子），在这个环境里看不出区别。** 噪声远大于这点差异
5. **整段往返（约 600 µs）基本由网络决定。** 交接段省下 100 多微秒，在整段里被网络抖动淹没了，第 ③ 组整段的差异分不出快慢。第 ④ 组整段甚至是“挤共享核”那边更低，这是网络噪声造成的，没有实际意义。真实交易系统要先把网络降到微秒级，这些软件优化才看得出来
6. **为什么课程判定全是“不能用”：** 课程要求 AUTO 每轮前后半段的往返中位数变化不超过 20%。EC2 的网络抖动经常超过这个门限。课程的规则是**宁可判不能用，也不事后放宽门限**。所以本次结论只能当作“方向参考”，不能当作正式测量结果

### 过程中的问题

- 第一次运行 ③ 中途报 `position limit`：AUTO 策略在后台交易，持仓碰到了风控上限。持仓回落后重跑成功。失败的记录保留在 `03-spsc-spin-failed-position-limit/`

## 第 07 章：XDP，在网卡驱动层丢一个行情包

数据：[20261124T1029Z-07-xdp/](../aws-runs/20261124T1029Z-07-xdp/)

### 怎么做的

1. 在 `.2` 上安装 clang 14、libbpf、bpftool 7.4
2. 课程的 XDP 程序 `flle_xdp_mold_itch.c` 只改 3 个常量：源 IP 改成 172.31.10.43，目标从组播 233.74.125.32 改成单播 172.31.12.156，端口从 31032 改成 42121
3. 编译成 BPF 对象（`elf64-bpf`，有 `xdp`、`.maps`、`.BTF` 段）
4. 为了让 ENA 支持**原生 XDP**：MTU 从 9001 临时降到 1500，队列从 4 个降到 2 个
5. 用 `ip link set dev enp39s0 xdpdrv obj ...` 挂载：程序 id 70，`jited`（已编译成本机指令），模式是原生驱动（不是 generic）
6. 先“全部放行”，重启回放，确认行情 HEALTHY
7. 再“只丢 1 个 NVDA 新订单”，看行情接收程序的反应
8. 卸载 XDP，把 MTU 和队列恢复原样

### 结果

**放行 5 秒内 XDP 看到的包：**

| 计数器 | 5 秒增量 |
|---|---|
| 课程行情 UDP 包 | 53,931 |
| AAPL 新订单 | 6,160 |
| NVDA 新订单 | 26,951 |
| 其他 ITCH 消息 | 20,820 |
| 被丢弃 | 0 |

**丢一个包之后：**

| | XDP 记录 | 行情接收程序 |
|---|---|---|
| 序号 | 丢了 **71089**（NVDA，locate 8095），共 1 个 | `next_expected=71089`，`gap_size=1` |
| 状态 | | `integrity=GAP`，`trading_gate=INHIBITED_FEED_GAP`（自动停止下单） |

判定：**`XDP_DROP_GAP_MATCH_PASS`**

### 第一次失败了，原因值得记住

第一次运行时，修改 MTU 和队列数会让**网卡短暂重置**，重置那一瞬间丢了行情包。行情接收程序在序号 1930496 处就已经进入 GAP 状态，后面 XDP 再丢包时，两边的序号就对不上了。记录保留在 `attempt1-nic-reset-gap/`。

修正：网卡准备好、XDP 挂好之后，**先重启回放**，开一个新 session（0612260002），确认 HEALTHY 后再丢包。课程原脚本也是这样做的。

**教训：** 在生产环境改网卡参数（MTU、队列、挂 XDP）会造成瞬间丢包，交易系统必须在**收盘后**做，或者先把这条行情线切到备用路径。

### 学到的

- XDP 在包**进入 Linux 网络协议栈之前**就处理，可以过滤、丢弃、计数
- BPF 程序每读一个字段前都要先检查边界（`data_end`），否则内核的校验器（verifier）不让加载
- MoldUDP64 的序号机制能**立刻**发现丢包，接收程序会自动停止交易，防止用不完整的行情下单
- AWS 的 ENA 网卡**支持原生 XDP**，但有限制：MTU 不能超过约 3498，队列只能用一半
