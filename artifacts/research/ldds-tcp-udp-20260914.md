# LDDS 与客户行情接口的 TCP、UDP 边界

第一章 `01-cn-access-relationships.png` 中，DDS/SDS—VDE—VSS 的 TCP 标注符合上证信息的 LDDS 正式接口说明书。客户侧使用 UDP 组播，在中泰 XTP-Pro 生产行情接口中有明确依据。两段协议可以不同；但把两份资料拼接起来，并不能证明某一家服务商实际通过 LDDS 取得了这一路客户行情。[1][2]

修订前的教材图把左侧泛称为“客户行情接口”，没有指定服务商、环境和传输协议。因此，准确读法是“上证信息 LDDS 接入段使用 TCP；服务商交付给客户的协议按其接口确定，例如 XTP-Pro 生产行情采用 UDP 组播”。右侧的 TCP 不需要改成 UDP，左侧则需要补充产品范围。

| 图中连接 | 原始资料能够确认的协议 | 原始位置 |
| --- | --- | --- |
| DDS 与信息商 VDE | TCP 长连接，承载实时行情 | LDDS 1.2.3，第 11 页 §2.4.2；第 13 页 §2.9 |
| SDS 与信息商 VDE | 按需建立 TCP 短连接，处理数据重建等请求 | 同上，§2.4.2、§2.9、§4.5 |
| VDE 与 VSS | 实时、重建两个 TCP 接口；STEP 重建连接按请求结束 | 同上，第 11 页 §2.4.3；第 17—19 页 §4.2—4.5 |
| XTP-Pro 生产行情服务器与客户 API | UDP 组播；指引要求连接同机房行情服务器 | 中泰《行情服务接入前指引》§1.1、§4.3—4.4 |
| XTP-Pro 公网测试行情服务器与客户 API | TCP | 同上，§1.1、§4.1 |
| 未指定服务商的客户行情接口 | 无法由 LDDS 总册确定 | LDDS 总册只约束自身接口；教材没有限定这一箭头的客户产品 |

上表前三级的依据是同一份正式 PDF。[1] 第四、五级来自中泰自身的客户接口文档。[2] 最后一行是对证据范围的判断。

DDS 是发布端的数据服务器，SDS 承担数据重建和认证；VDE 是上证信息提供的接入程序，VSS 是信息商的接收系统。官方架构图在第 10 页止于 VSS，并没有把中泰、Wind 或其他具名服务商的客户接口接在其后。教材下方的“客户行情程序”属于课程补充的业务关系，不能当作官方给出的传输协议。[1]

“行情通常使用 UDP 组播”适合作为一类实时分发设计的概括。IP 组播能够把一个数据报交给一个接收组；UDP 本身不保证可靠、有序到达，所以行情产品需要另行设计完整性处理。[5][6] TCP 则为一条连接提供可靠、有序的字节流。[4] 协议选择与每段连接的用途有关，不能仅凭“行情”或“Level-2”决定。

同一服务商可以接收上游 TCP 数据，在应用中处理后，通过自己提供的 UDP 接口向客户发送。这是两段独立的应用通信关系。它解释了为什么两段协议不同并不矛盾，但不是中泰上游实际部署已获证实的结论。

“服务商到上证都是 TCP”同样范围过大。上交所技术公司的行情广域接入产品明确提供 UDP 接入，公开承载 Level-1 FAST 和期权行情。[3] 这里应始终保留“上证信息 LDDS”这个产品限定。

TCP 的网络重传与行情的业务补发也要分开。前者修复当前连接的字节流；后者补回应用缺少的业务记录。举一个机制示例：程序停机期间没有有效行情连接，重连后开始接收新消息，新的 TCP 连接不会自行找回停机期间的历史业务记录。这个例子解释可靠传输的边界，不代表已经定位某次真实缺口的根因。[4]

LDDS 总册明确让 VSS 判断消息连续性，并对支持重建的数据向 VDE 重建端口发请求。VDE 转给 SDS，结果由 SDS 经 VDE 返回 VSS。快照类数据不支持该重建机制。教材应把这条路径称为应用层数据补发，不要让读者误以为 TCP 会跳过缺失字节、直接向应用交付后面的字节。[1][4]

XTP-Pro 客户端的丢包恢复则属于该客户产品的接口。中泰指引 §2.5 给出了客户端回补接口，不能把客户的请求直接画成向 LDDS SDS 发请求。[2] 服务商到 VSS 的完整性和服务商到客户的完整性，是两个分别需要处理的问题。
